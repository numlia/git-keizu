This shard and `13-keyboard-accessibility-02.md` hold the `web/main.ts` side of Feature 061-05 (keyboard operation and accessibility). Candidate selection, menu movement and cycling inside a dialog belong to each component's owner (`web/dropdown-test.md` S11 to S12, `web/contextMenu-test.md` S9 to S10, `web/dialogs-test.md` S9, `web/refOverflow-test.md` S6, `web/fileTree-test.md` S6, `web/findWidget-test.md` S11, `web/branchCleanupPanel-test.md` S7, `web/fileHistory-test.md` S12, `web/pathHighlightController-test.md` S2), and pure target resolution and guards belong to `web/keyboardNavigation-test.md` S1 to S4; they are not in this table.

**Common fixture**: `tests/web/main.keyboard.test.ts` builds a real DOM the same way as `tests/web/main.pathHighlight.test.ts`. It does not mock `Dropdown` / `ContextMenu` / dialogs / `FindWidget` / `FileHistoryController` / `RefOverflowController` / `Graph`, and controls only the host API (`acquireVsCodeApi().postMessage`) and the layout API (`clientHeight` / `getBoundingClientRect`). The standard fixture has display order `N → M → R` (parent of `N` is `M`, parent of `M` is `R`), `head = "M"` and no details. A "details request" is a `postMessage` with `command: "commitDetails"`, and a "compare request" one with `command: "compareCommits"`. "Consumed" means `defaultPrevented === true`, "not consumed" means `false`. Key operations send `keydown → keyup` as one sequence, and Escape observes `keydown` and `keyup` separately. Real Tab movement, native button clicks, IME and screen readers are not produced by jsdom, so those Cases keep manual check steps in Notes and are not counted in the automated test pass (§3.7.5 verification principle).
