## S52: getFileHistory() lineage continuation after a rename

> Origin: Bug fix (git-2-56-follow-lineage)
> Added: 2026-10-28
> Status: active
> Supersedes: -
> Signature: `private async queryFileHistoryLineage(repo: string, anchorHash: string, requestedPath: string): Promise<LineageResult | null>`
> Target Path: `src/dataSource.ts` (`queryFileHistoryLineage()`, right after `getFileHistory()`)
> Test File: `tests/src/dataSource.test.ts`

Since Git 2.56, `git log --follow` keeps one path per commit, and a commit reached from two history lines takes the path of the line Git walks last. When the line that went through the rename is walked first, the lineage query loses every entry before the rename. For each rename it follows, `getFileHistory()` runs the lineage query again on the old path and splices its groups after the rename commit (`src/fileHistory-test.md` S9). This table covers the spawn order, the args, and `null` at each failure stage of that continuation through the `cp.spawn` mock.
